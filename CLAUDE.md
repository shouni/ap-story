# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**ap-story** is an MCP-capable manga/comic generation orchestrator service (Go, Cloud Run + Cloud Tasks). It turns a manuscript (URL or text) into chapters → script → character design sheets → panels → pages as async jobs, persisting artifacts and a state document (`comic_state.json`) to GCS. All actual generation logic (script, design sheets, panels, pages) is delegated to the external [`go-comic-kit`](https://github.com/shouni/go-comic-kit) library — this repo's job is job management, async execution, history, and API/MCP exposure, nothing else.

Two callers hit the same JSON API: browsers via Google OAuth session, and AI agents (e.g. Claude) via service-account OIDC (M2M).

## Architecture

### Layering

```
main.go → internal/config → internal/server → internal/builder → internal/app.Container
                                                      │
                        assets (embedded HTML templates, CSS/JS, prompt templates)
                        internal/adapters (external SDKs: Gemini, Slack, Cloud Tasks, characters.json)
                        internal/pipeline (Worker: Task → Steps → go-comic-kit Ops)
                        internal/repository (GCS comic_state.json history: list/get/delete)
                        internal/domain (core types: Task, JobID, ports/interfaces)
                        internal/server/handlers (HTTP handlers, shared by JSON API and HTML views)
```

- **`internal/domain`** holds the core types and constructs nothing — no clients, no I/O, and what it takes from libraries is vocabulary and pure helpers only (`go-job-kit`'s `jobstatus` / `paging`, `go-comic-kit`'s `MangaState`, `go-utils`'s `jobid`, `remoteio.BuildURI`). It carries `Task` (job submission/validation), job ID generation/validation (`job_id.go` — job IDs are the single point HTTP input and GCS paths are sanitized through; always route new ID-consuming code through `ValidateJobID`/`SanitizeJobID`. Minting delegates to `jobid.New("c")` from `go-utils`, producing `c-{date}-{time}-{hex12}`; IDs minted before that change used `c{date}-{time}-{hex8}` and stay in GCS forever, so **never sort job IDs lexically** — `-` sorts below `2`, which would park every new job behind every legacy one. Use `jobid.SortKey`, as `history_listing.go` and `character_history.go` do), and the `TaskQueue`/`ComicRepository`/`Notifier` interfaces (`ports.go`) that other layers implement/consume. Add new cross-cutting interfaces here, not in `app`.
- **`internal/app.Container`** is the DI container — a plain struct of already-constructed dependencies (`Store`, `go-comic-kit` `Ops`, pipeline `Runner`, `TaskQueue`, `ComicRepository`, character definitions, HTTP client). It holds no construction logic itself. `Store` is a `remoteio.Store` — one window for read/write/list/sign, taken from `factory.Store()`. The GCS factory keeps the client lifetime and is what goes into `Closers`; go-remote-io used to hand back a `Bundle` of three separate components, which every app then threaded around in pairs.
- **`internal/builder`** contains the factory functions that build `Container` (`app.go`: `BuildContainer`) and the HTTP handler bundle (`handlers.go`: `BuildHandlers` → `AppHandlers{Auth, Web, Worker, M2M}`). This is where config values turn into live clients (GCS, Gemini, Slack, Cloud Tasks). If a resource fails to init partway through `BuildContainer`, already-created closers are cleaned up via the deferred error path — follow that pattern when adding a new external resource.
- **`internal/pipeline`** is the Worker side: `Runner.Run` takes a `domain.Task`, resolves output directories (job's `comics/{jobID}`, `design-jobs/{jobID}`, shared `character/`), asks a `Planner` for the ordered `Step` list for the task's command, and executes steps sequentially against `go-comic-kit` `Operations`. Steps live in `step_*.go` (one per pipeline stage: script, design, panel, page, state). `pipeline.New` validates required deps at construction time (fail fast at startup, not mid-job). Notification (Slack) failures never fail the job — they're logged only.
- **`internal/repository`** reads/writes `comic_state.json` on GCS directly (no database). History listing enumerates GCS prefixes without reading full state for unselected pages, and uses a TTL cache (`ttlcache`, `NewHistoryCache`) for history summaries. **`GetState` distinguishes a state that is not there yet from one it could not read** — `domain.ErrStateNotFound` vs `domain.ErrStateUnavailable`, split on `os.ErrNotExist` (which `remoteio` wraps not-found in, and go-comic-kit's `store.Load` passes through with `%w`), so no extra round trip. It used to collapse every failure into one "not found" error *and* discard the cause, which put a permission error and a GCS outage on screen as 「作品がありません」 with nothing in the logs. Handlers map the two through `writeStateError` (404 vs 502 + logged cause); the detail page shows its 「処理中かもしれない」 page only for the first, since telling someone to wait does not help when waiting will not fix it. The two errors demand opposite decisions, which is why `cleanupDesignJobState` treats only the missing case as "nothing to clean up" and reports the unreadable one instead of silently leaving a dangling reference. Same split as `go-job-kit`'s `jobstatus.ErrNotFound` / `ErrUnavailable`.
- **`internal/server`**: `router.go` wires chi routes. Two parallel auth paths share one composer (`auth.Protected(m2m, session)`): it first tries M2M (OIDC Bearer) verification, and falls back to browser session (cookie + CSRF) if that was not attempted. A bearer that *was* presented and failed now stops at 401 rather than redirecting to login. Worker routes (`/tasks/generate`) are OIDC-verified separately as Cloud Tasks calls, not user-facing.
- **`internal/server/handlers`**: **one handler per resource, not one per format.** `job.go` holds the four that people and agents both read — the job list, a job (status plus, once the state exists, the comic under `comic`), the character list, a character — and picks HTML or JSON from `Accept` (`gcp-kit/negotiate`, which also sets `Vary: Accept`). They used to be two handlers each, and the pair's own comment said "データ取得は JSON API と同一で、レスポンス形式だけが HTML になります" — exactly the shape that drifts when a fix lands on one side. Everything with no counterpart on the other side stays separate: input forms, `regenerate`, `status`, `script` read/write, the image redirects. The `/api` reads that duplicated them are gone; the MCP gateway calls the merged paths directly. Other files are one concern each: `{resource}_handler.go` for screens, `{resource}_api_handler.go` for machine-only endpoints.
- **`internal/adapters`**: thin wrappers around external SDKs — `ai.go` (Gemini/`go-comic-kit` operations wiring), `characters.go` (loads `go-character-kit` characters.json from GCS or local, falls back to the kit's embedded defaults), `slack.go` (Notifier impl), `tasks.go` (Cloud Tasks enqueuer). `adapters/prompts` implements the kit's prompt ports and parses the templates; the template files themselves live in `assets/prompts/`.
- **`assets`**: every embedded resource that is edited on a different cycle from the code — HTML templates, CSS/JS, prompt templates, the style presets (`prompts/styles.json`) — matching the sibling apps. It holds embeds and path constants only; loading and parsing belong to the consumer (`internal/server/handlers`, `internal/adapters/prompts`). Keep it that way: a sibling app's equivalent package accumulated six files of logic and stopped being a single-purpose location. Co-locating an embed with its consumer is still right for something one package owns privately — `go-comic-kit`'s `internal/prompts/templates` is the contrast.

### Async job model

Generation is multi-stage and long-running (minutes to ~10+ min), so everything runs as a Cloud Tasks job, never inline in a request:

1. `POST /jobs` (or `POST /jobs`（`command=generate_design_sheet`）) mints a job ID and enqueues a Cloud Tasks task, returning the job ID immediately.
2. The worker (`POST /tasks/generate`) receives the task and runs `pipeline.Runner`, which executes `go-comic-kit` operations and saves state (`comic_state.json`) to GCS.
3. Clients poll `GET /jobs/{jobID}` to read state/progress.

**The `queued` record is written before the enqueue, never after** (`handlers.recordQueuedStatus`, called from `enqueueAndRespond`). The worker reads `status.json` before it works and skips a job that already reads `succeeded` (`statusRecorder.begin`, the redelivery guard), and Cloud Tasks delivers in tens of milliseconds — so writing `queued` after the enqueue lets the next command on the same job (`render_comic` after `compose_comic`, a panel regeneration after a render; the status is per job ID, not per command) read the previous `succeeded` and be dropped silently. A failed `queued` write is logged and the enqueue still goes ahead: it is a GCS problem, not a reason to refuse the job.

Idempotency: state saves are always full overwrites (`store.Save` semantics from `go-comic-kit`), so re-running a step is always safe. Cloud Tasks task names (`Task.TaskName`) are `{jobID}-{command}[-{target}]`, and **every command except `compose_comic` appends the submission second** (`Task.repeatable`), so deduplication only collapses "the same target, submitted in the same second" — a caller's retry or an at-least-once redelivery, the duplicates worth merging. Naming a task by its target alone looked right and was wrong: `render_comic` exists to be re-submitted (resume from a failure), and `regenerate_*` / `generate_design_sheet` are "not good enough, again" operations, so all of them are re-submitted to the same target on purpose. Cloud Tasks keeps rejecting a finished task's name for a nominal hour (in practice longer), gcp-kit's `EnqueueWithName` treats that `ALREADY_EXISTS` as success, the caller gets a 202, and the job sits at `queued` with nobody processing it. No error surfaces anywhere, which is why the same panel's regeneration once no-op'd for hours before anyone noticed. `compose_comic` is the one command without the timestamp because it is only ever submitted with a freshly minted job ID (`newComposeTask`), so its name already differs per submission and a deterministic name can only ever collapse a resend of the identical request. A new command should default to the timestamped side: duplicating is safer than dropping.

State is saved at every phase boundary, and `Runner.savePartialResults` saves whatever exists before reporting a step failure, on a context detached from the caller's — being cut off by `PIPELINE_TIMEOUT` is precisely when the results are worth keeping. Without it a run that died on panel 40 of 64 left those images in GCS referenced by nothing.

A Cloud Tasks redelivery therefore resumes rather than restarts: `compose_comic` begins with `LoadStateIfExistsStep`, and each phase skips what is already done — `OutlineStep` returns early when chapters exist, `AllChapterScriptsStep` skips chapters that already have panels (regenerating one would replace them and drop their generation records), and the batch steps run with `SkipGenerated`. This is safe because `compose_comic` is only ever submitted with a freshly minted job ID, so an existing state means a re-run. Keep that property when adding a phase: a step in this plan must be a no-op when its output is already present.

Pipeline commands (`Task.command`, dispatched by `Planner`): `compose_comic` (full run: outline → per-chapter script → all panels → all pages; does **not** include design sheets — those are generated separately via `generate_design_sheet`), `render_comic`, `regenerate_chapter_script`, `generate_design_sheet`, `regenerate_panel`, `regenerate_page`.

`compose_comic` with `stop_after_script` ends after the script so the result can be reviewed before paying for an image per panel; `render_comic` then fills in the panels and pages that are missing. **The browser form always sets it** — `EnqueueComicForm` hardcodes `true` and the checkbox is gone, because at submit time the outline has not run and nobody knows whether this is 15 panels or 41. Authorising a cost you cannot see is the wrong default when one mis-click is the whole work; the detail page asks for the same authorisation with the panel count on screen. The JSON API still honours the flag, since an automated caller submits knowing it cannot see the count either way. Because it skips what already exists, the same command also serves as the resume path, and the detail page offers it under one button whose wording follows which case applies.

`render_comic` also takes `stop_after_panels`, which ends the plan after `AllPanelsStep`. Pages are a composite of panels, so the same "look before you pay" gate that guards the script→panel step now guards panel→page: a page built from panels you have not looked at is a 2K generation you may pay for twice. There is no pages-only command — with the panels already recorded, running `render_comic` again skips every one of them and composes the pages. The detail page shows one button at a time (`pendingImages` per chapter and for the work), so the order is not something the operator has to remember.

`render_comic` also takes an optional `chapter_id`, which the batch steps pass to `BatchOptions.ChapterID` so only that chapter's panels and pages are generated. That is the cheap way to check a change: images are the expensive half, and the script already had a chapter unit. The detail page puts the button on the chapter card next to "台本を再生成", so both chapter-scoped actions live in one place. No new command — a whole-work render is the same command without the field.

Panels and pages go through the kit's batch operations (`Ops.PanelBatch` / `Ops.PageBatch`), which run at `MAX_CONCURRENCY` (default 1, i.e. serial). Those return partial successes alongside an error, so `AllPanelsStep` / `AllPagesStep` assign the returned state even when the call fails — dropping it would strip the images that were just generated and paid for.

### Script proofreading

Dialogue is edited through `GET`/`PUT /jobs/{jobID}/script` (the 台本 tab on the detail page), not by regenerating: `regenerate_chapter_script` rewrites the whole chapter, so it cannot fix one line, and it changes the panel breakdown, which breaks the correspondence with panels that are already drawn. What travels is `domain.ScriptDraft` — chapter headings and per-panel dialogue only, never the whole state: `GenerationRecord`s and page artifacts are outputs, not inputs, and the full state exceeds 100KB with prompts included. `ScriptDraft.ApplyTo` replaces only text, speaker and kind; **adding, removing or reordering panels is rejected**, because the `panel_id` sequence *is* the mapping to the generated panel images.

**Saving is not the goal.** Dialogue is drawn into the page by the image model at composition time (`TEXT_TO_RENDER` in `prompts/page.go`), so a saved script leaves the pages showing the old text; `affected_pages` in the `PUT` response names the pages that must be composed again, which the detail page then offers. Panels stay valid, since they are generated with `No speech bubbles, no text`.

State saves are "always overwrite, always latest" and go-comic-kit's store has no conditional-write hook (`ifGenerationMatch`), so an edit that overlaps a running job is a last-writer-wins race with no trace. It cannot be prevented, so `rejectWhileJobIsRunning` answers 409 while the job's status is `queued` or `running`. A job with no status record at all passes through — refusing on "cannot tell" would make every work created before status recording existed permanently uneditable.

### GCS layout

```
gs://{STORY_BUCKET}/
├── comics/{jobID}/                    # per-work-job prefix
│   ├── comic_state.json               # MangaState — single source of truth for a job
│   ├── status.json                    # job status (queued / running / succeeded / failed), go-job-kit
│   └── images/
│       ├── panel_{panelID}.png
│       └── comic_page_{N}.png
├── design-jobs/{jobID}/
│   └── comic_state.json               # state for standalone design-sheet-only jobs (images live under character/)
├── character/{tag}/{jobID}.png        # design sheets — shared, work-independent assets
└── character-reference/{characterID}/... # human-curated master reference images (separate from AI-generated character/)
```

Character design sheets are stored outside `comics/{jobID}/` because a character can be reused across multiple works; `{tag}` is the character ID (or concatenated IDs for a composite sheet), and `{jobID}` is unique per generation call so regenerating a character never overwrites prior results. History listing enumerates `comics/*/comic_state.json`; design-sheet-only jobs live under `design-jobs/` instead and are surfaced via `/characters/{characterID}` rather than the main history list. Images are never served directly by the app — all image routes 302-redirect to a GCS signed URL. **Any code that turns a job ID into an HTTP path or GCS path must go through `domain.ValidateJobID`/`SanitizeJobID`** (see `internal/domain/job_id.go`).

### web / worker split

One image, two Cloud Run services (`ap-story` public, `ap-story-worker` private), selected by `SERVER_ROLE` (`cloudbuild.yaml` deploys both). The split buys three things: deployment settings per role (the worker needs a long timeout for minutes-to-tens-of-minutes generation, and the public face should not carry it), per-service logs and metrics (Cloud Run's built-in metrics are per service), and a task endpoint that is not public — co-located, `/tasks/generate` sits on the public service with only the in-app OIDC check in front of it; split, the worker's `internal` ingress and Cloud Run IAM reject the call before it reaches the container.

`SERVER_ROLE` has no default and an unset or unknown value fails startup. Treating unset as `both` would put `/tasks/generate` back on the public service the moment one production env var went missing. `builder` assembles only the role's dependency graph and `server.setupRoutes` registers only its routes: `web` builds the Cloud Tasks enqueuer and the session Firestore client and never constructs go-comic-kit `Operations` (the Vertex AI client), the Slack notifier or the pipeline, so `ap-story-web-runner` holds neither `aiplatform.user` nor access to `SLACK_WEBHOOK_URL`; `worker` builds none of the OAuth handler or the enqueuer, and verifies Cloud Tasks with `oidc.New` (audience + caller allowlist), which needs no OAuth secrets. `characters.json` is loaded on both roles, since the character screens need it on web and the pipeline on worker. `Container.Pipeline` is declared as `domain.Pipeline`, not `*pipeline.Runner`, because a nil concrete pointer stored in an interface field is a non-nil interface and the web role's nil check would stop working.

`SERVER_ROLE=both` with `go run .` shows the screens, but the pipeline never runs there: Cloud Tasks cannot deliver to localhost, so a submission enqueues and nothing arrives. Verify logic with `go test ./... -race`.

**The three timeout rungs have no defaults in the app, and the worker refuses to start without them.** `PIPELINE_TIMEOUT < TASK_DISPATCH_DEADLINE <= Cloud Run timeout`; the smallest wins, and Terraform is the only source for all three so the same number is never written in two places. Forgetting the dispatch deadline in Terraform would silently apply Cloud Tasks' own 10-minute default regardless of the Cloud Run timeout — which is why `validatePipelineTimeout` rejects an unset `TASK_DISPATCH_DEADLINE`, an unlimited `PIPELINE_TIMEOUT`, and equality as well as inversion. If Cloud Tasks cuts the request first, the process is stopped mid-job with no failure record, no partial save and no Slack notification, and `story-queue` has `max_attempts = 1`, so nothing retries and the job stays at `running` forever. Recording, notification and the partial save therefore all run on a context detached from the cancelled one (`gcp-kit/worker.Lifecycle` hands `Finish` a detached ctx; `savePartialResults` uses `context.WithoutCancel` with `partialSaveTimeout`). Raising `RATE_INTERVAL` has to be checked against this ladder first: `compose_comic` at the kit defaults is up to 84 AI calls, a 14-minute floor at `10s`, and the dispatch deadline caps out at 30 minutes, so there is little room to solve it by lengthening timeouts.

The worker's caller allowlist (`ALLOWED_TASK_SERVICE_ACCOUNTS`) names the **web** SA (`ap-story-web-runner`), not the worker's own: the SA on a task is the one Cloud Tasks mints the OIDC token as (`TASK_CALLER_SERVICE_ACCOUNT_EMAIL`, an enqueuer-side setting), and the worker only has to accept it. SA and IAM definitions live in the infrastructure repository's Terraform.

### Config

`internal/config` loads all settings from environment variables via `caarlos0/env`, grouped into `ServerConfig`, `GCPConfig`, `TasksConfig`, `StorageConfig`, `NotificationConfig`, `AIConfig` (mapped to `go-comic-kit`'s `ports.Config` via `AIConfig.KitConfig()`), and `AuthConfig` (Google OAuth for browser + allowed M2M service accounts for agent calls). Everything Cloud Tasks touches lives in `TasksConfig` (queue, worker URL, audience, allowed issuers) — the same grouping the sibling apps use. Two settings there are easily confused: `TasksConfig.CallerServiceAccountEmail` is the SA named on an outgoing task, which Cloud Tasks then signs a token as (an enqueuer-side setting, so web-only), while `TasksConfig.AllowedServiceAccounts` is the receiver's allowlist of **issuers** (worker-only). Neither falls back to the other; both are required on the side that needs them. `cfg.ValidateEssentialConfig()` is checked at startup in `main.go` before the server runs — extend it, don't add ad-hoc runtime checks, when a new required setting is introduced. `cfg.WarnOnContradictoryGenerationSettings()` runs alongside it for combinations that are legal but self-defeating: throughput is bounded by `1/RATE_INTERVAL` regardless of `MAX_CONCURRENCY`, and a `REQUEST_TIMEOUT` shorter than one image aborts generation rather than protecting it.

**Nothing that varies per work lives in config — not art direction, not model names, not the aspect ratio.** go-comic-kit's `Config` holds only run control (concurrency, rate interval, timeouts, limits, cache-control) and has no required fields; every per-work value rides on the request instead, with `Model` **required** on every call. Art direction lives in `assets/prompts/styles.json` and is chosen per job (see the style-mode section below); `STYLE_SUFFIX` and `DESIGN_STYLE_SUFFIX` are gone. Aspect ratio and image sizes still come from env (`IMAGE_ASPECT_RATIO`, `PANEL_IMAGE_SIZE`, `PAGE_IMAGE_SIZE`) but reach the kit per call, through `pipeline.Dependencies.Layout` — the app now owns that default, and moving it to the form is a live option. Model IDs rot on Google's release schedule, so nobody defaults them: `GEMINI_MODELS` and `IMAGE_MODELS` are comma-separated lists whose head is the default offered in the form, and `validateWebConfig` fails startup when either is missing — **on the web role only**. The worker never reads them: every job carries its own model names, so requiring them there would be demanding a value nothing consults. Concurrency, timeouts and the chapter/panel limits are the opposite case and keep their kit-side defaults, so leave those zero unless the deployment overrides them.

**A submitted job always names its models.** `Handler.newComposeTask` / `newDesignSheetTask` fill an omitted model with the head of the list rather than leaving it to the worker, the same call the aspect ratio already gets and for the same reason: the form and the JSON API must not answer differently. The picker has no 既定モデルを使用 option either, so a browser submission is explicit too. This is what lets the worker hold no model config at all, and it buys provenance — `MangaState.TextModel` / `ImageModel` name the models that actually made the work, which is what a later `render_comic` or chapter regeneration inherits. A job that reaches the kit with no model at all fails with `ErrInvalidRequest` before any AI call; today that can only be a state written before the picker existed.

**There is one image model, not two.** Design sheets, panels and pages all default to the head of `IMAGE_MODELS`. The kit used to split standard (panels) from quality (sheets, pages); which model counts as "quality" is Google's lineup talking, so the list's remaining entries are simply offered as choices in the forms instead.

**The image model is chosen where the images are paid for, not on the compose form.** At submit time the outline has not run, so nobody knows whether this is 15 panels or 41, or what the art will look like — the same reason the form no longer offers a whole-work run. The detail page's image buttons carry an image-model select instead, defaulted to whatever the work already recorded, and `Context.imageModel` writes the choice into `MangaState.ImageModel` on the first render so later chapters inherit it. That default is what keeps one work on one model; changing it is a deliberate act, which is also how you retry a chapter on the pro model.

**Three choices ride on a compose job: script mode, style mode, text model.** The compose form takes those three and `POST /jobs` takes them plus `image_model` (an automated caller submits knowing it cannot see the count either way); `handlers.validateChoices` rejects anything outside `GEMINI_MODELS` / `IMAGE_MODELS` and the loaded mode names, because a `<select>` binds the browser but not the JSON API. Every submission path goes through that one function — compose, design sheets and `POST /jobs/{jobID}/regenerate` — since splitting it is how the regenerate path ended up unvalidated the first time. They reach the worker on the `Task` (`TextModel` for the script, the existing `ModelOverride` for images — one image-model field serves compose and design sheets), and `OutlineStep` copies all four into `MangaState` (`TextModel` / `ImageModel` / `StyleMode` / `ScriptMode`). **Later jobs read the state, not the task**: `render_comic` after a `stop_after_script` gate, a chapter script regenerated from the detail page, and single panel/page regeneration all inherit the recorded choices, so one work is never half-written by one model and half by another. This is why no separate "image generation" screen exists — the detail page's existing buttons already carry the choices forward.

**Style modes are JSON, script modes are Markdown, and the split is deliberate.** A style (`assets/prompts/styles.json`, loaded by `prompts.Styles`) is three symmetric strings — `style` for panels/pages, `design_style` for sheets, and the `negative` that belongs with both — plus labels; Markdown would put one half in the body and the other in front matter, and they must change together. A script mode is a long templated prompt with `{{.}}` interpolation, so it stays one Markdown file per mode under `prompts/outline` and `prompts/chapter`, with YAML front matter (`direction` / `use_when` / `avoids` / `category`, same keys as the sibling apps) supplying the form's labels. `NewScriptPrompts` fails startup when the two directories disagree on mode names, since a mode offered in the form but missing on the chapter side would only surface mid-job. Unknown modes are errors, never a silent fall back to default.

**A design sheet takes `design_style`, never `style`.** The design-sheet form has its own style select, and `prompts.DesignPrompt` resolves the mode through `designSuffix`, not `imageSuffix`. The two differ by exactly the staging words — `cinematic lighting`, `dramatic rim lighting`, film grain — which must never reach a sheet: sheets are identity anchors, and lighting baked into one contaminates every generation that references it. `TestDesignStylesCarryNoLightingDirection` guards the presets and `TestDesignSheetUsesSheetSafeStyle` guards the wiring. Note that a generated sheet does **not** automatically become a panel reference — `characters.json` curation is still manual — so matching the sheet's style to the work's is a choice you make when curating, not something the pipeline enforces.

**The shared negative prompts must stay style-agnostic.** `panelNegativePrompt` / `pageNegativePrompt` carry only structure (text, anatomy, panel-count runaway); every colour word belongs to a preset's `negative`. `monochrome, black and white, greyscale` used to sit in the shared half, which meant a monochrome style would have been fighting its own generation — `TestStylePresetsDoNotContradictSharedNegativePrompts` guards that. For the same reason the page prompt says "follow the ARTISTIC STYLE instruction" instead of the old hardcoded "STRICTLY VIBRANT FULL COLOR".

**ページの割り付けはコマの中身が決めます。** `page_layout.go` の `planPageLayout` が段（tier）組みを組み立て、`page.go` は配置マップとコマごとの `POSITION` の両方をその1つの割り付けから書きます（以前は同じ規則を2箇所で計算していて、食い違う位置指示が並ぶ余地がありました）。引きの画・叫び／効果音・場面転換・吹き出しの多いコマほど重みが大きく、上位のコマが全幅の見せゴマになり、残りが2コマずつの段に入ります。段の高さと段内の幅は百分率で明示され、合計は必ず100%です。一律の2列グリッドだと、台本が章頭に必ず置く `wide` のコマが半幅に潰れ、間を作るための無言の寄りが決めゴマと同じ大きさで並びました。半幅のコマが奇数にならないよう全幅の本数を調整するのは、余った1コマの段が結局全幅になり、段だけが増えるためです。

**Reference images are this app's responsibility, not the kit's.** Panels and pages resolve a character's reference through `ReferenceURLFor(aspectRatio)` (go-character-kit): an entry in `reference_urls` matching the generated ratio wins, otherwise it falls back to the aspect-agnostic `reference_url` — silently, since a missing match is not an error. Design-sheet generation deliberately reads `reference_url` only, so a generated sheet never becomes the input for the next one. Nothing feeds generated sheets back into `characters.json`; that curation is manual, and until a `3:4` entry exists there, panel and page generation runs on the aspect-agnostic master with the drift suppression switched off. `IMAGE_ASPECT_RATIO` therefore only pays off once the matching references are curated.

A design-sheet request without an aspect ratio is filled in by `newDesignSheetTask` with `DefaultDesignSheetAspectRatio` (16:9, which suits the default three-view turnaround), not left for the kit to resolve — the form and the JSON API must not answer differently. A sheet meant as a panel/page anchor is the other combination: 3:4 plus the single-view layout.

## Conventions worth knowing

- Comments and many identifiers/docstrings in this codebase are in Japanese; match the existing language when editing a file that's already documented in Japanese.
- Interfaces are defined where they're consumed (`internal/domain/ports.go`), and implementations assert conformance with `var _ domain.X = (*Impl)(nil)` (see `repository.go`). Follow this when adding a new adapter/repository implementation.
- Constructors that assemble multi-dependency structs (`pipeline.New`, `app.BuildContainer`) validate required fields at construction and return an error immediately rather than letting a nil dependency panic later at request time.
